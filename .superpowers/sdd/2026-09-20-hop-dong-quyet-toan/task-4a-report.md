## API handed to T4B

- `useIncomeExpenseActionSnapshots({actorId, organizationId}, voucherIds, enabled)` in `src/hooks/income-expenses/useIncomeExpenseActionSnapshots.ts`. Use the same hook for a visible page or selected ID. It returns React Query state, `readiness`, and rejecting `refresh()`; `readiness` is loading during every refetch and error after any failed refresh, even with cached data. Namespace `income-expense-action-snapshots`, keyed by org + actor + sorted unique IDs, distinct from permissive display route cache. No fabricated LEGACY route.
- `IncomeExpenseActionSnapshot` in `src/lib/incomeExpenseActionSnapshot.ts` extends the T3 action voucher with exact CAS (NULL preserved), amount, identity/source, recipient, evidence URLs, private `flowKind`, `birthState`, and scoped permission booleans. Parse envelope/scope failures reject the batch. A malformed row becomes `unavailable[id]='INVALID_SNAPSHOT'`; missing/invisible ID becomes `NOT_VISIBLE`, never a synthetic ready voucher. `readActionSnapshotBatches` chunks 200 IDs and rejects changed org authorization version/routes across batches. Client test covers 1005 IDs in 6 calls; no per-row browser requests.
- `usePostingCashbooks(scope, enabled)` in `src/hooks/income-expenses/usePostingCashbooks.ts` returns the same readiness/refresh protocol; namespace `income-expense-posting-cashbooks`, actor + org. It verifies current auth identity, paginates existing custody RPC 200 rows at a time, chunks RLS account metadata by <=100 primary keys, excludes other-org/deleted/virtual accounts, rejects malformed values and transport errors. A missing metadata row is a deliberate RLS omission; no data truncation is silently treated as full metadata. Empty valid result is different from read failure. Client test covers 1105 custody IDs / 12 metadata calls.
- Both hooks poll 30 seconds and refetch on focus. T4B must wire these namespaces to shared realtime invalidation (membership/role/override/scope/custody/routes + vouchers/items/postings + owning-source changes), and must revalidate before writes. A snapshot is a display/command input, not server authorization or an idempotency result.

## Backend design and factual scope

Migration allocated using repository generator: `supabase/migrations/20260920192452_shared_income_expense_action_snapshot.sql`.

`public.read_income_expense_action_snapshots_v1(p_organization_id uuid, p_voucher_ids uuid[]) RETURNS jsonb` is STABLE, SECURITY DEFINER, fixed search path, row_security on, authenticated execute only. Its owner is new `ie_action_snapshot_reader`: NOLOGIN, NOSUPERUSER, NOBYPASSRLS, no role/database creation, authenticated inheritance in one direction only. Users cannot SET ROLE to it or query private tables. The role gets only SELECT on the three ownership columns and five canonical birth-operation columns read by this function, plus EXECUTE on the private scope helper. No schema CREATE remains after owner assignment. Function body reads `public.income_expenses` through its existing authenticated RLS; there is no copied building/admin OR policy and no new public table policy.

Why existing readers were insufficient: `finance_v2_visible_vouchers()` only covers custodian/knower paths; `ie_supplement_can_read_v1()` has a prior building gate. Neither preserves all current Thu chi RLS paths. Also `organizations`/`organization_memberships` direct SELECT is super-only, so the non-bypass role cannot load the scope header directly. Private STABLE `app_private.income_expense_action_scope_v1(org)` checks current auth, ACTIVE organization, non-revoked/time-valid ACTIVE membership, with no admin shortcut, and calls existing pure `all_scoped_keys_v3`, route, strict-mode functions. Only the reader role may execute it. No row locks, writer permission calls, mutation, or birth adoption were added.

`permissions.cancel` represents canonical `income_expenses.cancel` at the voucher building. Actual source confirms canonical cancel and flex use that key; legacy UI delete/collector ownership semantics remain distinct. **T4B must resolve cancel via existing income/flex/fallback eligibility and must not treat this canonical boolean as every cancellation dispatcher’s authority.** Similarly, money-edit eligibility is not inferred from owner alone here; T4B/T5 must use the actual sparse/flex/freeze capability. Permission scopes come from the existing pure reader; the actual writer still validates its permission, period, ownership and CAS.

Birth states are facts: `MISSING` when the three header birth fields are absent, `COMMITTED` for a matching completed canonical create operation under the same org/source hash and prior birth transaction, `INVALID` for a present canonical/unowned chain that fails that check, `UNVERIFIED` for a distinct domain-owned chain. No raw source hash or idempotency data is returned. T4B must apply the actual dispatcher’s birth requirements, not categorically block all legacy/domain-owned vouchers. The root shared aggregate `live-birth-presence.json` found missing header fields zero in the sampled pending kinds; that proves presence only, not committed-chain validity. No real rows were backfilled.

Existing `list_cashbooks_for_expense_v2()` keeps its id/name signature and now delegates each candidate to current `assert_cashbook_access_v2` under ACTIVE org. This preserves the exact writer membership/possession time windows and covering DENY semantics, with no admin shortcut. Only expected 42501 authorization denials omit a candidate; unexpected errors propagate. Ordering is stable for pagination. Virtual-account filtering remains in shared posting metadata boundary. `useCustodianCashbooksV2` old cache/fallback stays unchanged; it is not authority for the new hook.

The dedicated role is a forward migration/backup-restore dependency. Root read-only shared preflight (`live-role-capability.json`) confirmed PG17.6 postgres is not superuser but has CREATEROLE, BYPASSRLS, authenticated ADMIN/SET/INHERIT and schema privileges. Local rehearsal explicitly modeled a non-superuser deployment role. It caught and removed an unnecessary self ADMIN-option regrant; only explicit INHERIT/SET membership remains for function replacement/ownership. First apply and reapply passed and were rolled back. Rehearsal substitutes isolated names and the deployment-role name; it does not claim production apply occurred.
