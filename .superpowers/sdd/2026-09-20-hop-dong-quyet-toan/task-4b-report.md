## Result and API

`useIncomeExpenseActions({scope:{actorId,organizationId},voucherIds,onEdit?,refreshRequired?})` owns the common batch/selected snapshot, strict action contexts, immutable confirmation snapshot, routes, versions, caller key, pending write plus refresh, classified outcome and reconciliation. It returns `contexts`, `availability(id)`, `selected`, `selectedAvailability`, `open(action,id)`, `openApproval(id)`, `close`, `busy`, `dismissalBlocked`, `outcome`, `cashbooks`, `retryable`, and `commands.{confirm,retry,reconcile}`. `refreshRequired` lets the settlement host await its own required reader. Use `openApproval` only to resolve a not-yet-loaded existing legacy/canonical approval intent; it never falls back after a canonical error or a route change.

Both `src/pages/payments/IncomeExpensePage.tsx` and `IncomeExpenseMobilePage.tsx` now instantiate this controller with the active organization and actor. Desktop List gets actual `actionContexts` and all action callbacks; desktop/mobile detail get the same controller, action buttons and dialog host. Selected/batch-child IDs are loaded by the same batch reader. Replaced Page handlers and duplicate confirmation/posting dialogs were removed. Create/import/recurring/batch cancellation/restore/copy/history remain their existing separate operations.

`IncomeExpenseActionDialogs` hosts the existing posting and supplement forms. Posting retains subject VOUCHER, execution revision 0, exact two CAS versions including zero, stable caller key, exact approved amount, selected current cashbook, and all four adopt/attach/remove/upload evidence callbacks. Evidence uploads and unconfirmed operations block dismissal. Legacy approval retains its account/evidence picker; existing real-account restriction for shareholder vouchers is preserved. `IncomeExpenseActionButtons` is shared by both detail surfaces; old non-controller consumers retain their existing toolbar compatibility.

`buildIncomeExpenseActionContext` combines only runtime-validated snapshot, current custody and existing cancellation eligibility. `useIncomeExpenseCancellation` batches both existing income/flex readers at <=100 IDs, scoped by org+actor+sorted IDs, and fails closed on transport/parse/missing-row errors. The policy no longer requires raw `.cancel` for income/flex writers. It chooses fallback only for actual `STRICT_MODE` / `NOT_MANUAL` signals and still requires the existing adapter's authority; the server remains final authority. No component calls a raw source RPC.

## Lifecycle, money and authorization

- Review resubmit uses the reviewed hook on the existing voucher ID and review CAS/key. It sends no patch, creation, approval, posting, amount or source change. Supplement remains append-only and does not transition review, including cancelled and legacy vouchers.
- Preflight re-reads the current authorized voucher and strict route, checks scope and immutable money/source/status/version fingerprint, then runs the shared policy. It does not replace the user's reviewed CAS with a freshly loaded version. Current custody and cancellation are independently represented as readiness: unrelated cancellation/custody transport failure cannot grant authority or suppress an otherwise valid review write.
- Canonical approve keeps `financeV2Mutations` owned dispatcher (invoice/termination refund and actual forfeit pair); explicit legacy approval keeps its own existing writer. There is no canonical failure to legacy retry. The forfeit writer has no caller-key/CAS contract; the controller never blindly retries its uncertain result.
- Post-only permits the existing approved UNPOSTED/REVERSED path; approve-and-post requires UNPOSTED. Missing CAS, owned unsupported post/reverse, invalid birth, engine/freeze restrictions, unknown routes or insufficient permissions stay disabled with a reason. Unapprove requires actual CAS and its existing admin UI authority; known canonical payload freeze is represented as unsupported instead of attempting a guaranteed failing write.
- Income cancellation uses the existing keyless income door; expense flex gets both CAS; legacy/source cancellation retains the existing guarded ladder and owned fallback. Reverse requires the exact currently held voucher cashbook and reverse permission. No amount/source/maker guard is weakened. The old adapter's server error/fallback behavior remains its responsibility.
- Managed mutation options suppress duplicate success/toast/invalidation so the controller owns the whole write/refresh outcome; existing non-managed callers retain prior behavior. Idempotent writers receive the same caller key on owned dispatch and explicit retry. Keyless legacy/unapprove/cancel are reconciliation-only when outcome is unknown. Review retry after permission revocation is denied before a second call.
- Confirmed write plus refresh failure is shown as “Đã xử lý, chưa tải lại được”, locks dismissal/commands and offers reconciliation. Unknown results retain the original payload/key; observed current state can be reconciled without another money request. A close is never success. Required mounted readers are awaited, unmounted readers invalidated for next open.
